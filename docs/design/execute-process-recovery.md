# `execute_process` recovery: how each final state is reached

`execute_process(COMMAND …)` is cmake's configure-time escape hatch —
it runs an arbitrary program while cmake configures, and projects use
it for everything from feature probes to code generation. The converter
has to decide, per call, what the Bazel equivalent is. This doc maps the
decision tree so you can tell *why* a given call became a build-time
genrule, a native rule, a loud refusal, or a convert-time bake.

The code lives in `converter/internal/lower/execute_process*.go`. The
entry point is `recoverExecuteProcess` (`execute_process.go:175`).

## The four terminal states

Every recovered call lands in exactly one of these:

- **(a) genrule** — a real build-time rule that re-runs the command (or
  an equivalent `cp`/tool invocation). The output is regenerated by
  Bazel on every relevant input change. Registered in `cc.OutToGenrule`.
- **(b) native rule** — an idiomatic Bazel rule (`proto_library` +
  `cc_proto_library`, a `bool_flag` + `config_setting` feature knob, a
  nested-cmake build). Wired to consumers via `cc.OutToNativeConsumerDep`
  / the second-pass nested driver.
- **(c) refusal** — the call has no faithful Bazel form, surfaced
  **loudly** as a Tier-1 failure (default) or a structured
  conversion-todo. Never silent.
- **(d) bake** — the configure already ran, so the output file exists on
  disk; the converter captures those bytes as a `write_file` (text) or a
  base64 genrule (binary). This is **convert-time** recovery: the bytes
  are frozen until the next `convert` run. The audit facet
  `cmake-codegen-execute-process-derived-bake` (and the build-dir
  `cmake-codegen-build-dir-bake`) ride the bake-warning channel.

States (a) and (b) are *live* (re-run at build time); (c) is *loud*; (d)
is *frozen*. The interesting question — and the source of "why did this
bake when a genrule looks possible?" — is the boundary between (a)/(b)
and (d).

## Dispatch

`recoverExecuteProcess` normalizes each call (`normalizeCMakeECall`,
dead-capture clearing), runs the cross-call `planUnspecifiedOutputs`
pre-pass, then `Classify(call)` assigns a **bucket** and a `switch`
(`execute_process.go:213`) routes it.

```
execute_process(COMMAND … [OUTPUT_FILE] [RESULT_VARIABLE] …)
        │  normalize + Classify → bucket
        ▼
┌─ BucketCMakeE  ("cmake -E <op>")  ──────────── liftCMakeE (:215)
│     copy / copy_if_different / copy_directory / create_symlink /
│     rename / touch / tar(create)  ─────────────────────▶ (a) genrule / pkg_tar
│     configure_file ── liftCMakeEConfigureFile (:1599):
│         ├ template==output & bytes equal      ─────────▶ (no rule; same-path mirror)
│         ├ copy-only / values resolve          ─────────▶ (a) cmake_configure_file
│         └ bytes differ / values unresolved     ─────────▶ (d) bake  ◀ lift downgrade
│     make_directory / remove* / compare / sleep / true… ▶ benign skip
│     lifter precondition fails (bad anchor)     ─────────▶ (c) refusal
│
├─ BucketFileProducing  (has OUTPUT_FILE)  ──── liftFileProducing (:1764)
│     out under build dir, argv rewritable      ─────────▶ (a) hoisted genrule
│     INPUT_FILE outside src / ERROR_FILE outside build /
│     WORKING_DIRECTORY unanchored / multi-CMD+RESULTS ──▶ (c) refusal
│
├─ BucketNestedCMake  (cmake -S/-B, --build)  ──────────▶ (b) native (2nd pass)
│
└─ default ── if BucketRefuse:
      ├ liftArgvFileProducing  (in/out files appear IN argv) ▶ (a) argv-codegen genrule
      └ liftUnspecifiedOutputs (:288) — outputs NOT in argv:
            ├ directory operand (protoc --cpp_out=<dir>)
            │     liftDirOperandOutputs (:305):
            │     rewrite operand → $(RULEDIR)/<dir>      ─▶ (a) re-run genrule
            │
            └ derived-name stem match (foo.proto→foo.pb.cc)
                  bakeDerivedOutputs (:459)  ───────────────▶ (d) bake  ◀ THE BRANCH
      else (probe / stamp / unrecognized) recoverProbeOrStampCall (:272):
            ├ feature-declaration probe ───────────────────▶ (b) bool_flag+config_setting
            ├ captured in dump-vars / forwarded set() ─────▶ benign skip
            └ otherwise ───────────────────────────────────▶ (c) refusal
```

## The bake-vs-lift boundary

Three places produce a bake instead of a live rule. Understanding which
one fired tells you whether a lift was genuinely impossible or merely
not yet wired.

### 1. `configure_file` value/byte downgrade

`liftCMakeEConfigureFile` (`execute_process.go:1599`) lifts a
`cmake -E configure_file` to the `cmake_configure_file` native rule when
the substitution values resolve and it isn't a degenerate same-path
identity. When the values can't be reconstructed (or the in/out bytes
differ in a way the lift can't express), it falls back to the byte-bake.
This is a *known incompleteness* of the lift tier, not a structural
impossibility.

### 2. The unspecified-output split: dir-operand re-run vs stem-match bake

This is the branch most likely behind "a genrule looks possible." For an
unrecognized `tool <inputs…>` whose outputs are **not** named in the
argv, `liftUnspecifiedOutputs` (`execute_process_unspecified.go:288`)
recovers the outputs declaratively from three signals the converter
already holds:

- **File API demand** — `cc.ConsumedBuildRel`: only build-dir files the
  build graph consumes need a producer.
- **ninja exclusion** — `cc.NinjaOuts`: anything with a build edge is
  already recovered; its absence is the orphan signal.
- **trace argv** — the producer linkage.

It then splits on *how the output is linked to the argv*:

- **Directory operand** (`protoc --cpp_out=<dir>`, `-d <dir>`): the tool
  is *told* where to write. `liftDirOperandOutputs`
  (`execute_process_unspecified.go:305`) enumerates the on-disk files
  under that operand as the outputs and emits a **re-run genrule** with
  the operand rewritten to `$(RULEDIR)/<dir>` — placement is sound
  because the tool writes where Bazel expects. State **(a)**.
- **Derived-name correlation** (`foo.proto → foo.pb.cc`): the output is
  *not* an argv operand, so the converter can't tell the tool where to
  write at re-run. `bakeDerivedOutputs`
  (`execute_process_unspecified.go:459`) captures the configure-written
  bytes instead. State **(d)**.

The split is deliberate. The code says so
(`execute_process_unspecified.go:456`):

> the re-run upgrade is writer-style-dependent and deliberately deferred.

Why it's hard rather than unfinished: the output *path* is known (the
codemodel records it), but the output *placement convention* is not. A
tool that writes **CWD-relative** can be lifted (run the genrule with
`cd $(RULEDIR)` so its writes land where Bazel expects). A tool that
writes **input-relative** cannot — Bazel `srcs` are read-only, so the
tool would try to write into the source tree. The trace doesn't reveal
which, so the safe default bakes. Declaring `outs` from the codemodel is
the easy, sound half; placement is the residual.

### 3. The indirect route — a refused call's output, baked at the consumer

A call that lands in **(c) refusal** still left its output on disk (the
configure ran). Later, when a codemodel target *consumes* that build-dir
file, `bakeBuildDirFile` (`build_dir_source_bake.go:56`) recovers it —
writer-index lift first, then the `--lift-download` path, then the
on-disk **byte-bake**. So a refused `execute_process` whose output is
consumed surfaces as a `write_file` bake **at the consumer**, not at the
call site. Widening the lift coverage upstream is what removes these.

## The codegen-recognizer registry, and its current reach

The registry (`codegen_recognizer.go`) is the sound way to lift a *known*
codegen tool: a recognizer `Match`es on the driver tool + argv shape and
`Lower`s to the idiomatic native rule, **cross-checking** its predicted
outputs against cmake's recorded outputs (`derivedOutputsConsistent`) so
a match is proof rather than a guess. It is operator-extensible via
Starlark recognizers (`starlark_recognizer.go`).

Today the registry is invoked from exactly one site —
`dispatchCodegenRecognizer` (`standalone_genrules.go:458`), the
`add_custom_command` path. **`execute_process` never reaches it.** So the
same `protoc` becomes `proto_library` + `cc_proto_library` via one cmake
spelling (`add_custom_command`) and a stem-match bake via the other
(`execute_process`). Closing that asymmetry — routing the
unspecified-output `execute_process` through `recognizeCodegenWith`
before the bake — plus the placement-aware generic re-run above, is
tracked in `ROADMAP.md`. One wrinkle that makes it more than a wire-up:
the recognizer's consumer wiring (`NativeRuleConsumerLabels`, consumed in
`emit/bazel/split.go`) is `#include`-header-oriented, but the typical
`execute_process`+protoc shape has the generated `.pb.cc` as a codemodel
**source** of a target — lifting that needs the source dropped from the
consumer's `srcs`/`hdrs` and replaced with a dep on the native rule.

## Where to look when a bake surprises you

1. Find the call's bucket + reason in the convert diagnostics
   (refusals carry `File:Line`, `Bucket`, `Reason`, `Argv`).
2. If it's a `configure_file` downgrade → the values didn't resolve
   (boundary #1).
3. If it's `[unknown]`/`BucketRefuse` with a stem-matched output →
   `bakeDerivedOutputs` (boundary #2); the genrule re-run is the
   deferred upgrade, gated on output placement.
4. If the bake appears at a *consumer* with no execute_process at that
   site → a refused call's output recovered downstream (boundary #3).

See `ROADMAP.md` for the planned closures (the `execute_process` →
recognizer routing and the placement-aware derived-output re-run).
