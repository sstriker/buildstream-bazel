# `execute_process` recovery: how each final state is reached

`execute_process(COMMAND …)` is cmake's configure-time escape hatch — it
runs an arbitrary program while cmake configures, for everything from
feature probes to code generation. The converter decides, per call, what
the Bazel equivalent is. This doc maps the decision tree so you can tell
*why* a given call became a build-time genrule, a native rule, a loud
refusal, or a convert-time bake.

The code is in `converter/internal/lower/execute_process*.go`; the entry
point is `recoverExecuteProcess` (`execute_process.go:175`).

## The four terminal states

- **(a) genrule** — a real build-time rule that re-runs the command (or
  a `cp`/tool equivalent). Regenerated by Bazel on input change.
  Registered in `cc.OutToGenrule`.
- **(b) native rule** — an idiomatic Bazel rule (`proto_library` +
  `cc_proto_library` from the codegen-recognizer registry; a
  `bool_flag` + `config_setting` feature knob; a nested-cmake build).
  Consumers wired via `cc.OutToNativeConsumerDep` / the 2nd-pass driver.
- **(c) refusal** — no faithful Bazel form, surfaced **loudly** (Tier-1
  failure, or a structured conversion-todo). Never silent.
- **(d) bake** — the configure already ran, so the output exists on disk;
  the converter captures those bytes as a `write_file` (text) or base64
  genrule (binary). **Convert-time**, frozen until the next `convert`.

(a)/(b) are *live*; (c) is *loud*; (d) is *frozen*. The interesting
question is the boundary between (a)/(b) and (d).

## Dispatch

`recoverExecuteProcess` normalizes each call, runs the cross-call
`planUnspecifiedOutputs` pre-pass, then `Classify(call)` assigns a bucket
and a `switch` (`execute_process.go:213`) routes it.

```
execute_process(COMMAND … [OUTPUT_FILE] [RESULT_VARIABLE] …)
        │  normalize + Classify → bucket
        ▼
┌─ BucketCMakeE ("cmake -E <op>") ───────────── liftCMakeE
│     copy / rename / touch / tar(create) …          ─────▶ (a) genrule / pkg_tar
│     configure_file ── liftCMakeEConfigureFile:
│         ├ copy-only / values resolve               ─────▶ (a) cmake_configure_file
│         └ bytes differ / values unresolved          ─────▶ (d) bake  ◀ downgrade #1
│     make_directory / remove* / compare / true …    ─────▶ benign skip
│
├─ BucketFileProducing (OUTPUT_FILE) ── liftFileProducing ▶ (a) hoisted genrule / (c)
├─ BucketNestedCMake (cmake -S/-B --build) ──────────────▶ (b) native (2nd pass)
│
└─ default ── if BucketRefuse, in order:
      ├ liftRecognizedExecuteProcessCodegen  ────────────▶ (b) native rule
      │     recognizer registry (protoc --cpp_out → proto_library +
      │     cc_proto_library); supplies outputs + on-disk-corroborates
      ├ liftArgvFileProducing (in/out files IN argv) ────▶ (a) argv-codegen genrule
      └ liftUnspecifiedOutputs — outputs NOT in argv:
            ├ directory operand (--cpp_out=<dir>)
            │     liftDirOperandOutputs: operand → $(RULEDIR)/<dir> ▶ (a) re-run genrule
            └ derived-name stem match (foo.in → foo.gen.cc)
                  ├ --lift-derived-codegen: cd $(RULEDIR) re-run ▶ (a) genrule  ◀ #2 live
                  └ default:                  bakeDerivedOutputs  ▶ (d) bake    ◀ #2 bake
      else (probe / stamp) recoverProbeOrStampCall:
            ├ feature-declaration probe ───────────────────▶ (b) bool_flag+config_setting
            ├ captured in dump-vars / forwarded set() ─────▶ benign skip
            └ otherwise ───────────────────────────────────▶ (c) refusal
```

## The codegen-recognizer registry and its reach

The registry (`codegen_recognizer.go`) lifts a *known* codegen tool to
its idiomatic native rule: a recognizer `Match`es on driver + argv shape
and `Lower`s to the rule, **cross-checking** predicted outputs against
cmake's recorded ones (`derivedOutputsConsistent`) so a match is proof,
not a guess. It is operator-extensible via Starlark recognizers
(`starlark_recognizer.go`, `--recognizers`).

It is reached from a single chokepoint, `recognizeOrGenrule`
(`codegen_recognizer.go`), wired into **all three** codegen-emit paths:
the `add_custom_command` standalone path (`standalone_genrules.go`), the
per-target ninja `recoverGenrule` (`genrule.go`), and the
`execute_process` supply path (`liftRecognizedExecuteProcessCodegen`,
first in the `BucketRefuse` default). So the same `protoc` lifts to
`proto_library` whether spelled as `add_custom_command` or
`execute_process`. On the execute_process path the recognizer is the
output AUTHORITY: the outputs aren't recorded (protoc derives them from
`--cpp_out=DIR`), so the recognizer supplies them and the converter
corroborates against the on-disk + codemodel evidence before emitting.

## The bake-vs-lift boundary

Three places still produce a bake. Which one fired tells you whether a
lift was impossible or merely not (yet) applicable.

### 1. `configure_file` value/byte downgrade

`liftCMakeEConfigureFile` lifts `cmake -E configure_file` to the
`cmake_configure_file` native rule when the substitution values resolve.
When they can't (or the in/out bytes differ in a way the lift can't
express), it byte-bakes. A known incompleteness of the lift tier.

### 2. Unspecified-output split: dir-operand re-run vs stem-match

For an unrecognized `tool <inputs…>` whose outputs are **not** named in
the argv, `liftUnspecifiedOutputs` recovers the outputs from three
signals the converter holds: File-API demand (`cc.ConsumedBuildRel`),
ninja exclusion (`cc.NinjaOuts`), and the trace argv. It then splits on
how the output links to the argv:

- **Directory operand** (`protoc --cpp_out=<dir>`): the tool is *told*
  where to write, so `liftDirOperandOutputs` rewrites the operand to
  `$(RULEDIR)/<dir>` and emits a **re-run genrule** — placement sound
  regardless of writer style. State **(a)**.
- **Derived-name correlation** (`foo.in → foo.gen.cc`): the output isn't
  an argv operand, so the tool can't be told where to write at re-run.
  - Default: `bakeDerivedOutputs` captures the configure-written bytes.
    State **(d)**.
  - **`--lift-derived-codegen`** (opt-in): `liftDerivedOutputsRerun`
    emits a **live genrule** that re-runs the tool with `cd $(RULEDIR)`
    so its cwd-relative write lands where Bazel expects, with
    `$(location)` inputs made absolute (`$$ROOT/…`) so they survive the
    cd. Sound only when every orphan sits at the **build root** (a
    cwd-relative write resolves there); a deeper output path, a
    non-re-runnable tool, or an unstageable input declines back to the
    bake. State **(a)**. Off by default because flipping it changes
    every corpus convert with a stem-match codegen → needs a corpus
    byte-sweep to validate (see `ROADMAP.md`).

Why placement is the hard half: the output *path* is recorded by the
codemodel, but the *placement convention* (cwd-relative — liftable via
`cd $(RULEDIR)` — vs input-relative — unliftable, since `srcs` are
read-only) is not. The build-root guard is the conservative slice that's
provably cwd-relative (the configure ran the tool with cwd = build dir,
and a build-root orphan landed there); the input-relative writer's output
lands in the *source* tree and never reaches this build-dir-scoped path.

### 3. The indirect route — a refused call's output, baked at the consumer

A call that lands in **(c) refusal** still left its output on disk. When
a codemodel target later *consumes* that build-dir file,
`bakeBuildDirFile` (`build_dir_source_bake.go:56`) recovers it (writer-
index lift first, then `--lift-download`, then the on-disk byte-bake) —
so a refused `execute_process` whose include-only output is consumed
surfaces as a `write_file` bake **at the consumer**, not at the call
site. Widening upstream lift coverage is what removes these. (Note
`bakeBuildDirFile` skips any output already claimed by a native rule via
`outputClaimed`, so a recognized output is never double-produced.)

## Where to look when a bake surprises you

1. Find the call's bucket + reason in the convert diagnostics (refusals
   carry `File:Line`, `Bucket`, `Reason`, `Argv`).
2. `configure_file` downgrade → values didn't resolve (boundary #1).
3. `[unknown]`/`BucketRefuse` with a stem-matched output →
   `bakeDerivedOutputs` (boundary #2); `--lift-derived-codegen` upgrades
   it to a genrule re-run when placement is sound.
4. A bake at a *consumer* with no execute_process at that site → a
   refused call's output recovered downstream (boundary #3).

See `ROADMAP.md` for the remaining closures (default-on for the
recognizer + the derived-output re-run, both gated on a corpus
byte-sweep; the configure_file value reconstruction; and the
execute_process rebased-`--proto_path` residue).
